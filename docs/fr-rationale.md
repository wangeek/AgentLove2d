# FR 核心机制：为 Agent 的图形化验证而设计

> 本文回答一个问题：**为什么这套机制存在**。FR 帧流不是又一个"录制回放工具"——它是为了让 AI agent（LLM）能够**可靠地验证图形程序的行为**而设计的中间表示。规格见 fr-spec.md，机制细节见 love2d-gap.md / design.md，本文讲设计动机与推理链。

## 一、问题：图形程序对 Agent 是不可验证的

Agent 写代码已经很成熟了，但"写游戏/写图形程序"始终卡在一处：**Agent 无法验证画面**。

- **像素不可推理**：LLM 的本职是符号操作（读代码、diff 文本、比对行）。一帧 640×480 的像素阵列是连续场数据——不可 grep、不可锚行、不可命名。diff 两帧像素只知道"变了"，不知道"谁做了什么"。
- **截图验收不可再生**：让多模态模型"看一眼"截图判断对不对，结论随模型版本漂移、不可复现——它不能进任何回归判据。
- **GPU 内部不可判**：纹理布局、混合次序、驱动差异——GPU 优化自由度越大，"同一份代码"的输出越不确定。

一句话：**图形程序的行为产物（像素）恰好落在 Agent 最不擅长的表示域里**。

## 二、解法：把"画面"翻译回 Agent 的母语——符号行

FR 的全部设计可以从一句话推出来：

> **让一帧的全部可判定事实，以符号行的形式存在。**

```
frame 3
  clear 0 0 0 255
  draw 1 0 11.000020 20.000000 0.000000 1.000000 1.000000 0.000000 0.000000 255 255 255 255
  print 2 "L0" 12.000000 340.000000 0.000000 1.000000 1.000000 255 255 0 255
  rect 0 0.000000 456.000000 640.000000 24.000000 0.000000 0.000000 1.000000 255 0 0 255
```

这一帧对 Agent 是完全可工作的对象：

| Agent 操作 | 在像素世界里 | 在 FR 里 |
|---|---|---|
| "画面变了吗" | 几十万字节 diff，无语义 | 两帧行 diff，逐行可读 |
| "精灵在动吗" | 目测/光流 | `draw` 行 x 坐标链 11→12→13（qf 域精确） |
| "这个 UI 元素出现了吗" | 模板匹配（脆弱） | `grep 'print 2 "L0"'` |
| "回归测试" | 截图对比（驱动/缩放敏感） | fr-check 锚行判据，字节级稳定 |
| "哪一帧开始错" | 二分播放视频 | fr-bisect 首分歧帧，纯文本二分 |
| "为什么错" | 无从下手 | 分歧帧的 in 段事件 + log 段状态 + out 段决定并排 |

## 三、五条设计原则（全部由此动机导出）

1. **符号与字节的两层验证律**（D3）：日常回归锚符号行（grep/diff 的母语），终审用定长字节相等（脚本算，Agent 读结果）。**任何一环都不需要"理解像素"**——agent 调脚本读数字，不做视觉判断。
2. **capture-then-replay = 视觉真源唯一**（D8）：屏幕显示的就是 IR 的回放，不是另一条渲染路径。这保证"Agent 验证的流"与"用户看到的画面"是同一个东西——验证流即验证画面，无需二次信任。
3. **确定性模型**：固定 dt、RNG 单咽喉、量化域 %.6f、墙钟只进注释——同一输入必产同一流。**Agent 的验证结论因此可复现**，这是能进回归判据的前提。
4. **双形态 + 单一真源表**：.fr 文本给 Agent 读，.frb 二进制给机器，互转逐字节相等。命令集从 cmd.tbl 生成——Agent 改表可以，手写编解码不行，一致性由生成器守。
5. **tee 分岔消费**（tee₁文件/tee₂屏幕）：Agent 消费 tee₁ 的落盘文件，用户消费 tee₂ 的屏幕——同一份帧缓冲，互不干扰。无头模式（拓扑 C）= 屏幕消费者缺席，文件就是全部——**agent 在 CI/服务器上跑无头验证，与玩家桌面完全同构**。

## 四、Agent 工作流（实证过的闭环）

这套机制在 B4-2 已跑通最小闭环，Agent 的典型工作循环是：

```
写/改内核 Lua 代码（普通 love.graphics API——无新 DSL 要学）
  ↓ FR_CAPTURE=1 运行（无头或带窗）
产 .fr 会话文件（tee₁）
  ↓ Agent 直接读：文本行，grep/diff/锚行
  ↓ fr_check：canonical 幂等 + sha 对账 + CHECK 判据
  ↓ fr-as/fr-dis：双形态互转（round-trip 逐字节）
  ↓ fr-bisect：对拍两版会话，二分首分歧帧
定位到行 → 定位到代码 → 修 → 重跑 → 会话 diff 收敛
```

对比传统循环（跑游戏→截图→人看/多模态猜），每一步都换成了可再生的符号操作。**B0-B4 全部批次的开发过程本身就是用这个循环做的**——78 项测试里没有一项依赖像素理解，Canvas 回读断言也是脚本读数字。

## 五、为 MCP 工具预留的接口面

将来把这套能力包成 MCP 工具给 agent 直接调用，接口面已经天然就位——**每个工具对应一个已有的 CLI/API，MCP 层只是薄封装**：

| MCP 工具（设想） | 底层 | Agent 用途 |
|---|---|---|
| `fr_record` | love.exe + FR_CAPTURE（拓扑 C） | 跑一段会话产 .fr/.frb |
| `fr_read` / `fr_grep` | fr_session + fr_codec_gen parse | 读流/按 op/帧/字段过滤（比 dump 更结构化的返回） |
| `fr_check` | fr_check 判据 | 提交前回归（幂等+sha+CHECK） |
| `fr_diff` | 两流逐帧 diff | 行为对拍（改前 vs 改后） |
| `fr_bisect` | 首分歧帧 | 定位回归起点 |
| `fr_stats` | op 频度/结构 | 理解会话概况 |
| `fr_screenshot` | tee₂ 离线回放 + 符号摘要 | **视觉问题的符号结算**：不返回图片，返回差异矩形/计数/hash（D10 符号结算律——agent 要的是"哪里变了"的符号，不是像素） |

> **实施口径（2026-11-02 精简，实装=三件）**：用户拍板 MCP 面只留 agent 自己做不方便的事
> ——`fr_record`（env 组装）/`fr_read`（大文件读，默认剥资产 hex）/`fr_diff`（双流对齐，
> 吸收 fr_bisect 首分歧帧语义）。`fr_grep`/`fr_check` 砍（read 后 agent 自过滤/自判——
> 文本已在上下文里，再包一层是伪原子）；`fr_stats`/`fr_screenshot` 暂缓（无评价锚/待取
> 证）。全量字节体与结构化消费走 CLI（fr_dump 不带 --strip-assets 即 canonical 原文）。
> 实装见 `tools/fr_mcp.py`。

设计约束（从本机制直接继承）：
- MCP 工具**只流通文本与数字**（行、矩形、CRC、计数）——不流通图像字节，与"Agent 读符号"的原则一致；
- `fr_record` 在无头拓扑下可在服务器/CI 运行，产物与桌面录制逐字节一致（确定性模型保证）；
- 判据脚本（CHECK 行）随仓库走，MCP 的 `fr_check` 执行它——工具无状态，状态全在流与判据文件里。

## 六、与"agent 写游戏"的总图景

FR 是**验证层**，不是创作层：agent 用普通 LÖVE API 写游戏（创作），用 FR 验证（置信）。两层之间零额外学习成本——内核代码不知道 FR 存在，验证工具不修改内核行为。这套分离意味着：

- 换内核（另一个游戏、AI 生成的关卡逻辑、逆向移植的前端）验证方法不变；
- 换消费者（人的眼睛、CI 的判据、MCP 工具的返回）流格式不变；
- 将来 agent 自我改进循环（写→跑→验→修）的每一步都有可再生的判据——这是让 agent 独立完成图形程序开发的信任地基。
