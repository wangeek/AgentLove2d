# FR 流在 agent 开发流程中的实践报告

> 数据来源：MemoryRemake / memory_love（LÖVE 重制工程）自 2026-11-09 起的实战使用，
> 主会话 `mvs_21ee8251c8f64761aa3be88a75a22199`，以及该仓 `docs/PLAN.md`、
> `tools/fr_smoke.py`、`checks/*.txt`、`smoke/out/` 落盘产物。
> 报告口径：只写实测到的数字与复盘结论；未实测的判断标注为"推断"。
> 编写日期：2026-11-18

## 0. 一句话结论

FR 流在这类「界面 + 状态机」游戏上**能当主验证手段**——本项目的 39 项冒烟判据里，
绝大多数由流断言承担，agent 无需看图就能判断行为对不对；但**成本结构不在断言上**：
92% 的时间花在进程启动与封口等待，判据本身几乎不耗时。因此真正的工程杠杆是
**录制路径的稳定化与并行化**，而不是把判据写得更细。

## 1. 实际应用规模（实测）

| 指标 | 实测值 | 备注 |
|---|---|---|
| 判据文件 | 23 份（`checks/*.txt`） | m0~m21 分模块，一模块一份 |
| 冒烟项 | 39 项 | 曾 42 项，撤掉 3 项重复后 |
| 全量冒烟耗时 | **72 秒**（原 121 秒） | 并行化后；`FR_JOBS` 可调 |
| 单次录制进程启动 | 31 次 → 现 39 项内多次复用 | 每项至少一次 love 启动 |
| 真正"跑游戏"时间 | **< 10 秒**（占全量 8%） | 其余 92% 是启动 + 封口等待 |
| 单流体积（全量档） | 10.2 MB / 10 帧 | 本仓典型：字体 1.56MB + 图集 1.71MB + 背景 |
| 单流体积（精简档） | **93 KB（1.4%）** | `fr_slim.py` 剥资产载荷后 |
| 单流体积（.frb） | 5.0 MB（49%） | 文本 hex → 二进制 |
| 落盘流总数 | 75 条 | `smoke/out/` 累计 |
| 落盘产物目录 | 22 GB | **其中一条失控流占 20.4GB**（见 §6.1） |

## 2. agent 实际怎么用 FR：五步闭环

`tools/fr_smoke.py` 把方法论固化成机械判据，agent 每次改完跑一遍即可：

| 步骤 | 断言 | 失败含义 |
|---|---|---|
| L1 纯逻辑自检 | `MEMORY_LOGIC: PASS` | 数据/布局层坏了（不进 FR） |
| R1/R2 双录 | 同帧数、同字节数 | 录制路径不稳定（启动/封口竞态） |
| D1 确定性 | `fr_diff` → `FIRST-DIVERGENCE -1` | 有不确定源（随机/墙钟/输入污染） |
| D2 扰动定位 | dt 0.016→0.02 必**帧 0 分叉且落 dt 行** | 扰动没生效，或流没按预期结构写 |
| F1/F2/F3 判据 | 正例 rc=0；负例必 FAIL | 判据本身失效（锚错/太宽） |

**这五步的价值顺序**（实测体会）：D1 最重要——它一红，后面所有判据的绿灯都不可信；
D2 是 D1 的对照，防止"两次跑出同样的错"被误判成确定性；F3 最便宜但最容易被省略，
而它正是防止判据空转的唯一手段。

## 3. 判据写作的四条实证纪律

### 3.1 锚结构量，不锚像素
本项目的判据全部锚**调试状态行**（`FRAME pos=52/52 phase=storyDone`、
`SAND s= blank=1`、`TIMER sec=0.50 clock=00:01`），由游戏在 `FR_DEBUG=1` 下输出。
理由：沙盘坐标随牌局变化，绝对像素不可锚；而"行数/列号/折返次数/要素计数"是语义。

### 3.2 判据分层——FR 只验 FR 能验的
`M3`（答对推进/答错不推进/全对通关）曾被写成三条 FR 判据，后**全部撤掉**：
逻辑回归里已有同内容的断言，FR 层再验一遍只是多三次进程启动。
判据文件 `m3.txt`/`m3_wrong.txt`/`m3_clear.txt` 一并删除，不留死文件。

### 3.3 动画必须能定格，否则判据不稳定
`FR_DRAW=1`（抽牌动效冻结在展示中段）、`FR_WIN=0.9`（胜利动画定格在勋章弹出后），
这类"冻结钩子"是判据可用的前提——动效中间帧不可复现，锚不到。
同理，计时类断言把 `dt` 放大到 0.5（10 帧 = 5 秒），才能断言准确秒数而不是"看起来在动"。

### 3.4 把"前提"也写成可验证项
窗口录制会捕获真实 OS 输入（鼠标碰一下帧 0 就混进 `mousepressed`，实测两次流
A=192618 / B=192445 立刻分歧）。对策三层：录制自带"无输入"重试（最多 3 次）、
判据里显式 `CHECK-NOT: ev 0 "mouse`、逻辑层不读输入（动画只吃 dt）。

## 4. 录制路径的六个坑（都踩过，代价可数）

| # | 坑 | 症状 | 对策 |
|---|---|---|---|
| 1 | 普通游戏**无头不推进帧** | `FR_HEADLESS=1` 录不出任何帧 | 一律窗口模式录制（`FR_HEADLESS` 只对显式补帧的 rig 有效） |
| 2 | 游戏不会自己退出 | 等它退 → 必然 180 秒超时（白等两次） | 轮询帧数到点后 `terminate()` + 封口缓冲 0.8s |
| 3 | 窗口输入污染 | 双跑字节数不同 | 见 §3.4 |
| 4 | 存档串味 | M4 期望 `sprite=13` 实际读到 M5 存的 `sprite=21` | 每项测试前 `reset_profile()` + `FR_IDENTITY` 隔离身份 |
| 5 | 环境变量传中文 | 台词写进存档变 GBK 字节，下次渲染抛 `UTF-8 decoding error` | env 通道只走 ASCII；中文走存档文件 |
| 6 | love.exe 是 GUI 子系统 | stdout 无处可写，自检结论丢失 | 结论走文件旁路（`FR_LOGIC_OUT`） |

## 5. 体积治理：三档形态各司其职

| 形态 | 体积 | 用途 | 边界 |
|---|---|---|---|
| `.fr` 全量 | 10.2 MB | 回放、抽素材 | 判据用它纯属拖慢磁盘 |
| `.fr` 精简（`fr_slim.py`，载荷换 `-`） | 93 KB（1.4%） | **判据链路默认** | 不能物化资产、不能回放 |
| `.frb` 二进制 | 5.0 MB（49%） | 长期留存 | 大行解析 O(L²)，`fr_dis` 回环会卡死 |

**关键纪律**：精简只换载荷，不换结论——判据必须验"全量档 rc == 精简档 rc"（本项目 S2 项）。
精简阈值按 12% 而不是卡 10%：剥离量稳定 ~90%，剩下的是每帧必需的字体行；
卡死阈值会在"多加一张小图"时误报。

## 6. 失败面与未解问题

### 6.1 失控流：一条 20.4GB 的调试产物（本报告最贵的一课）

`smoke/out/m14_dbg.fr` = 20.4 GB，会话头 `sha` 全零、`seed=0`——手工调试录制没设
`FR_FRAMES`、没给表指纹。逐行扫描（本报告取证时实测）：

| 指标 | 实测 |
|---|---|
| 体积 | 20.4 GB |
| 行数 | 184,062,957 |
| 帧数 | 366,659（60fps 下约 1.7 小时连续录制） |
| 资产行 | 93 |
| 行前缀分布 | `poly` 71.5M / `line` 57.2M / `rect` 45.5M / `print` 6.6M / `clear` 1.1M |
| **最长单行** | **2,218.7 MB（2.2 GB），且以 NUL 字节开头** |

三个独立问题叠在一条流里：

1. **无帧上限**：`FR_FRAMES` 缺省不限帧，手工调试跑了一小时四十分钟没人管。
2. **每帧绘制量爆炸**：单帧平均约 500 条 `poly`/`line`/`rect`（71.5M+57.2M+45.5M ≈ 1.74 亿行
   ÷ 36.7 万帧）——这是调试视图把大量图元逐条写进了流。
3. **文本流里出现二进制**：那条 2.2GB 的行在**第 3108 行、帧 6**（前一行是上一帧的
   `d_crc`），以 NUL 字节开头、以 ` 255\n` 结尾——形如"缓冲前段未初始化、尾部才是真内容"。
   后果之一是**整条流对文本工具失效**——`grep -c "^frame "` 在这条流上返回 0 命中
   （grep 判为二进制直接放弃），也就是这条流已经无法被任何按行消费的工具读取。

**教训**：调试录制比冒烟录制更危险（没人管帧上限）；`FR_FRAMES` 应与 `FR_CAPTURE` 同生。
而"文本流里混进 NUL + 2.2GB 单行"这条，症状指向捕获层某条路径把**未初始化缓冲**当成行内容
写盘并算错了行长（本报告只取证到现象与位置，未定位到代码路径）。这类流一旦产生，
`fr_check`/`fr_diff`/`fr_dump` 全部不可用——**它同时是一条不可判定的流**。

配套现状：本仓 `smoke/out/` 已 22 GB，说明**流的生命周期管理**（定期清理/分层留存）
在实战里是缺失的一环，而非小问题。

### 6.2 `.frb` 的大行解析
1.5MB 字体行在 `fr_dis`/`fr_check` 上会退化为 O(L²)，实测卡死 180 秒以上。
现状对策是"不碰"：`.frb` 只验体积减半，正确性交给 AgentLove2d 的 pytest。
这是**工具面的已知缺口**，不是使用方的问题。

### 6.3 静默降级与判据全绿
音效与徽章素材缺失时游戏 `pcall` 静默降级，画面照跑、判据全绿——曾导致"全程没声音
但测试通过"。对策是让缺省可断言：`RANKS loaded=N fringe=N` 两层分开报，
判据 `m13` 断言 `badges=4`。

## 7. 对工具族的建议（按实测收益排序）

1. **给 `fr_record` 加"帧数必填"或默认上限**——§6.1 的 21.8GB 是可避免的。
   （现状：`frames` 可选，缺省不限帧。）
2. **录制配方固化成工具参数**：窗口模式 + 到点 terminate + 无输入重试 + 身份隔离，
   这四条每次手写必然出错；`fr_record` 目前只做 headless，窗口路径得由使用方自建。
3. **精简档下沉为工具开关**：`fr_slim.py` 是使用方自己写的，但它服务的需求（判据链路剥离载荷）
   是通用的——建议并入 `fr_dump`/新增 `fr_slim` 到工具族。
4. **`.frb` 大行解析修 O(L²)**：这是唯一"建议使用方绕开"的缺口，绕开本身就是成本。
5. **`--geo` 已被验证有效**（本仓 `tools/fr_geo.py` 直接调用 `fr_dump --geo`）：
   `# geo: d1 tex=94 rect=30.78,78.00 316.44x178.00（img 1280x720 @0.247222）`
   取代了"自己乘 ox/sx/oy/sy"的手工推算，建议在 agent-guide 里提到更靠前的位置。
6. **`fr_lint` 增加"不可判定流"诊断**：行内出现 NUL 字节、或单行超过阈值（如 64MB）时
   直接报错退出。§6.1 那条流最贵的地方不是占 20.4GB，而是**它静默地变成一条读不了的流**，
   而工具链没有任何一处提示"这流坏了"。这条实现成本极低、收益是避免一整类误判。
   **✅ 已兑现（2026-11-18，L006）**：`fr_lint` 流式扫描行内 NUL / 单行超 256MB / 非法 UTF-8，
   越界即返——对 §6.1 那条流实测 **0.11 秒报出"行3108: 行内含 NUL 字节"**，
   与全量逐行扫描（约 4 分钟）位置一致；正常流（golden 与 10MB 实战流）零误报。

## 8. 一句话给下一个 agent

**先让 D1（双跑逐字节）站住，再写判据**；判据只锚结构量、只验 FR 特有的东西；
录制一律窗口模式 + 到点 terminate；判据链路喂精简档；每次改完跑一遍五步闭环。
